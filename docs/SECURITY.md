# ZyroPay Security

This document has three parts: the threat model, the controls, and who implements each control. Read it together with `ARCHITECTURE.md` §3 (trust boundaries) and ADR-001 (signing model).

## Assets

1. **User funds.** These are the keys inside Turnkey sub-organizations.
2. **Signing capability.** This covers user passkeys, Turnkey session keys, delegated-signer API keys, `INTERNAL_SERVICE_TOKEN` and OAuth tokens.
3. **Integrity of approvals.** What the user sees must be exactly what gets signed.
4. **Agent policy and spending state.** This covers limits, reservations and the ledger.
5. **Personal data.** This covers emails, addresses linked to identities, and push tokens.

## Framing (landing page embed)

By default the web app refuses every frame (`frame-ancestors 'none'`, `X-Frame-Options: DENY`). The landing page shows the real app inside an iframe on desktop, so the staging build allows exactly two parents:

- `https://zyropay.online` (the landing page);
- `http://localhost:4321` (the landing page's dev server).

The list lives in one place, `apps/web-host/scripts/build.mjs` (`FRAME_PARENTS`), and feeds three things: the CSP `frame-ancestors` directive, the `Permissions-Policy` for WebAuthn, and the bundle's `EXPO_PUBLIC_FRAME_PARENTS`. A `--env local` build allows only `http://localhost:4321`. Production allows nothing (`frame-ancestors 'none'`) and still sends `X-Frame-Options: DENY`.

**What changed in the threat model (T18).**

- `X-Frame-Options: DENY` is gone from staging. It cannot express an allowlist, and browsers that implement CSP `frame-ancestors` ignore it when both are present. Every browser ZyroPay supports implements `frame-ancestors`, so any origin outside the list is still blocked. The protection against clickjacking for every other origin is unchanged.
- The allowed parents can now overlay or crop the app. That is a UI-redress risk, so the landing page joins the trust boundary: its code, its hosting account and its dependencies must be held to the same bar as the web app. A compromise of the landing page could frame the app and try to trick a user into a click. Two things still hold. Every approval and signature needs passkey user verification in a browser-owned prompt that a page cannot draw over or fake. And the review screen shows what gets signed (C7).
- `localhost:4321` is allowed only on staging (testnets). Any program a developer runs on that port can frame the staging app. Remove it from `FRAME_PARENTS` if that is not acceptable.
- Storage inside the iframe is partitioned by the top-level site in current browsers. A session started inside the landing page's frame is not the session of the app opened directly, and the reverse is also true.

**What the app does when framed** (`apps/mobile/src/lib/embed.ts`, `embed-runtime.web.ts`):

- It sends the parent `{type:"zyropay:ready"}` once it has rendered. If the frame cannot use passkeys, it sends `{type:"zyropay:passkey-unavailable"}` instead. These are the exact messages the landing page listens for. They have no other fields and carry no user data.
- It sends only to an exact target origin, never `"*"`. That origin is the parent's, read from `location.ancestorOrigins` (Chromium, WebKit) or from `document.referrer` (Firefox). If it is not on the allowlist, or the browser does not reveal it, the app sends nothing.
- It never listens to `message` events, so the parent cannot drive it.
- If WebAuthn fails inside the frame with `NotAllowedError` or `SecurityError`, or the frame's Permissions Policy forbids WebAuthn, the app shows "Open ZyroPay in full screen to use your passkey". This is an `<a target="_top">` link to the same page. Passkeys always work at the top level.

**What the landing page does.** Its iframe carries `allow="publickey-credentials-get *; publickey-credentials-create *; clipboard-write"`, and its own `Permissions-Policy` delegates those features to the app's origin. Without that delegation, Chromium reports the features as disabled, and the app shows the full-screen link at once. If the iframe is sandboxed, include `allow-scripts allow-same-origin allow-forms allow-popups allow-top-navigation-by-user-activation`, or the full-screen link cannot navigate the tab. The passkey rpId stays the app's own host, so passkeys made in the frame and at the top level are the same passkeys.

## Rules for engineers

- Never accept, log or store a recovery phrase or private key (ADR-003); imports go device → Turnkey enclave only.
- Never log: stamped request bodies or headers, tokens, private keys, Turnkey activity payloads containing unsigned transactions, or full addresses next to emails.
- Never add a code path that signs without going through `transition()`, `evaluatePolicy()` (agent requests) and the payload-hash checks.
- Never compute money with `number`. Use the `money.ts` helpers.
- Never trust MCP-supplied `userId`. The API derives the user from `agentId`.
- New third-party calls must have timeouts and must fail closed.
- Never add an origin to `FRAME_PARENTS` (`apps/web-host/scripts/build.mjs`) without a security review, never use `postMessage(..., "*")`, and never make the app act on messages from a parent frame.
- Report vulnerabilities privately to the maintainers. Do not open public issues.
