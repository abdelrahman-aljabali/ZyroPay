# Auto-pay on Cardano (agent allowance)

An AI agent connected through the ZyroPay MCP connector pays small Cardano amounts **without a
passkey tap**. The limits are enforced **by the Cardano ledger**: the payment spends the user's
allowance UTxO at the Aiken allowance contract (`contracts/allowance`), and the validator refuses
anything outside the limits written into its datum. The passkey creates, tops up and revokes the
allowance; it never has to approve the individual payments inside it.

Status: preprod only, live from the app since 2026-10-31 ([Live run](#live-run-2026-10-31)). The
contract is not audited.

## Feasibility (verified)

- **x402 `exact` accepts an allowance spend.** `@x402/cardano` 2.29.0's facilitator does not
  require a key-hash payer, does not check who owns the inputs (it only resolves the nonce UTxO's
  address as `payer`), and accepts redeemers and an inline PlutusV3 script. It checks the vkey
  signatures it finds, value conservation over every input, the fee floor,
  `TTL <= now + maxTimeoutSeconds`, `validityStart <= now`, the payout to `payTo`, and asks the
  chain to evaluate the scripts. Proof, offline: `apps/seller/test/allowance-x402.test.ts`, which
  builds the spend with `planAllowanceAgentPay`, signs it with the agent key only and runs it
  through the official facilitator `verify()` (valid), with a failing script evaluation (refused),
  paying 1 lovelace too little (refused), and end to end through the seller app (HTTP 200,
  settled, the node received the exact bytes). The same transaction shape (agent pays the x402
  seller's `payTo` from the allowance) already passed the real ledger on preprod on 2026-10-30
  (`contracts/allowance/deployments/preprod.json`).
- **Fees and collateral** come from the agent key's own ADA ("float"): the allowance cannot pay
  them (the fee would count as `paid` and need a payee). The create transaction therefore also
  sends a float (default 5 ADA) to the agent address. One payment costs about 0.29 ADA in fees;
  collateral is posted, not spent.
- **One payment per allowance at a time.** The allowance is one UTxO, and the seller's
  facilitator only accepts inputs that are on chain, so the next payment waits for the previous
  one to confirm. While a payment is in flight, a new one falls back to passkey approval
  (`ALLOWANCE_BUSY`).

## Custody of the agent key

The agent key is an Ed25519 key **generated by the ZyroPay API** for each allowance, encrypted at
rest with AES-256-GCM under `DELEGATED_KEY_ENCRYPTION_KEY` (the key that already protects the
Solana/EVM delegated signer), bound to the user and allowance ids (AAD). The plaintext exists only
in memory while one payment is signed. Revoking destroys the ciphertext.

Why not a Turnkey-held key: Turnkey would sign the transaction body hash as an opaque raw payload,
so a Turnkey policy could at best restrict _which key_ signs, never _what_ it signs; the bound is the
on-chain validator either way. A Turnkey agent key also needs new passkey ceremonies (create the
key and a policy scoped to it) that the app does not have, and the delegated Turnkey user only
exists once the user enabled Solana/EVM autonomous mode. The server-held key has the same custody
class as the existing delegated signer (an encrypted key the API holds) and a strictly smaller
blast radius:

- the agent key can only spend the allowance, within the datum's limits, to the listed payees,
  until `expiresAt`, plus its own float;
- it can never move funds from the user's wallet (that needs the passkey);
- the owner (passkey) can take everything back at any time with one tap (`Owner` redeemer).

If the ZyroPay server is compromised, the most an attacker can take is what the limits allow
before the user revokes: `perPayment` per transaction, `perDay` per day, only to listed payees
(or to anyone, if the user chose "any payee").

## Policy

Auto-pay is evaluated after the agent's normal policy (`evaluatePolicy`):

1. A **deny** stays a deny.
2. A request is auto-paid only when it is `send` or `pay_x402` (direct `exact`, not Masumi escrow)
   on `cardano-preprod` in ADA, from the wallet that owns the allowance; the agent's own policy
   would only ask for approval because of `ALWAYS_ASK` or Cardano's `AUTONOMY_NOT_SUPPORTED` (any
   USD limit reason, `ESCROW_REQUIRED` or `VALUATION_UNAVAILABLE` still goes to the passkey);
   and, against the allowance as read **from the chain**: the payee's payment credential is on the
   list (or the list is "any"), `amount <= perPayment`, `spentInPeriod (+ roll-over) + amount <=
perDay`, the allowance holds `amount` above its minimum, it has not expired, the float covers
   fee + collateral, and no other spend of it is in flight.
3. Otherwise the request falls back to the normal passkey approval with the reason why
   (`ALLOWANCE_*` codes below). Auto-pay never turns an approval into a deny.

Fiat limits (EUR or USD) are converted to lovelace **once, at creation**, with the price service;
both are stored and shown. The chain only knows lovelace.

Masumi escrow payments keep the passkey: an escrow lock goes to the escrow script, whose refund
path needs the buyer's signature later; paying it from the allowance would make the agent key the
buyer and the refund would go to the agent, not to the user.

## Data model (migration `0008_cardano_allowance`)

- `cardano_allowances`: id, user_id, agent_id, wallet_id, network, status, owner_address,
  owner_key_hash, script_address, agent_address, agent_key_hash, encrypted_agent_key,
  limits (per_payment_lovelace, period_ms, period_cap_lovelace, period_start, expires_at,
  allowed_payees jsonb), fiat (currency, per_payment_minor, period_cap_minor, unit_price,
  priced_at), budget_lovelace, float_lovelace, utxo_tx_hash, utxo_index, datum_cbor,
  pending_action jsonb (the built owner transaction awaiting the passkey), create_tx_hash,
  last_tx_hash, in_flight_request_id, timestamps. One live allowance per agent (partial unique).
- `cardano_allowance_spends`: id, allowance_id, transaction_request_id (unique), payee,
  lovelace, tx_hash, status (`signed`/`submitted`/`confirmed`/`failed`), next utxo, next datum,
  timestamps.

## API (user, app)

All bodies and responses are JSON; lovelace amounts are decimal strings. Schemas live in
`packages/shared/src/cardano-allowance.ts` (`CardanoAllowanceSchema`, `AllowanceReviewSchema`, ...) and
the endpoints in `packages/shared/src/api/contracts.ts` (`getAgentAllowance`, ...).

### `GET /v1/agents/:agentId/allowance`

`{ allowance: CardanoAllowance | null }`. Reads the allowance UTxO from the chain on every call
(and moves `creating` → `active`, `revoking` → `revoked` when the chain shows it).

### `POST /v1/agents/:agentId/allowance` (create)

```jsonc
{
  "walletId": "uuid", // a Cardano preprod wallet of the user, shared with the agent
  "network": "cardano-preprod",
  "budget": { "lovelace": "20000000" }, // or { "fiat": { "currency": "EUR", "amount": "25.00" } }
  "perPayment": { "fiat": { "currency": "EUR", "amount": "10.00" } },
  "perDay": { "fiat": { "currency": "EUR", "amount": "20.00" } },
  "payees": { "mode": "list", "addresses": ["addr_test1..."] }, // or { "mode": "any" }
  "expiresInDays": 7, // 1..90
  "floatLovelace": "5000000", // optional, 3..20 ADA, default 5 ADA
}
```

→ `{ allowance: CardanoAllowance /* status "pending_create" */, review: AllowanceReview }`.
409 when the agent already has a live allowance. Repeating the call while `pending_create`
rebuilds the transaction (same allowance id, same agent key).

### `POST /v1/agents/:agentId/allowance/top-up`

`{ "budget": { "lovelace": "..." } | { "fiat": ... } }` → `{ allowance, review }`. An owner spend
that recreates the allowance with `old + added` lovelace and the same datum (the period counter is
kept). Only while `active`. The float is topped up with a plain send to `allowance.agentAddress`.

### `POST /v1/agents/:agentId/allowance/revoke`

No body → `{ allowance, review }`. An owner spend that returns everything in the allowance to the
wallet. Allowed while `active`, `exhausted` or `expired`. After the revoke is submitted the API also
returns the agent's float to the wallet (signed by the agent key; it pays the owner only) and
destroys the agent key.

### `POST /v1/agents/:agentId/allowance/submit`

`{ "bodyHash": "<review.rawPayload.payload>", "signRequest": StampedTurnkeyRequest }` →
`{ allowance }`. Exactly like an approval: the stamp must be the user's passkey over
`SIGN_RAW_PAYLOAD_V2` of that body hash with the wallet's key; the API re-verifies the stored
transaction, claims it once, attaches the witness, submits it and tracks it. A body hash that does
not match the pending build is refused (409).

### `GET /v1/agents/:agentId/allowance/spends?limit=20`

`{ spends: AllowanceSpend[] }`, newest first.

### Shapes

```ts
type Money = { lovelace: string } | { fiat: { currency: "EUR" | "USD"; amount: string } };

interface CardanoAllowance {
  id: string;
  agentId: string;
  walletId: string;
  network: "cardano-preprod";
  status:
    | "pending_create" // built, waiting for the passkey
    | "creating" // submitted, not on chain yet
    | "active"
    | "exhausted" // less than one minimum payment left; top up or revoke
    | "expired" // past expiresAt; revoke to get the rest back
    | "revoking"
    | "revoked"
    | "failed"; // create never landed
  ownerAddress: string; // the wallet
  scriptAddress: string; // the owner's allowance contract address
  agentAddress: string; // the agent key's address (holds the float)
  limits: {
    perPaymentLovelace: string;
    perDayLovelace: string; // period_cap with period = 1 day
    periodMs: string; // "86400000"
    expiresAt: string; // ISO
    payees: { mode: "any" } | { mode: "list"; addresses: string[] };
    fiat: {
      currency: "EUR" | "USD";
      perPayment: string;
      perDay: string;
      budget: string | null;
      adaPrice: string;
      pricedAt: string;
    } | null;
  };
  onChain: {
    utxo: string; // "<txHash>#<index>"
    balanceLovelace: string;
    spentInPeriodLovelace: string; // after roll-over, as the next payment would see it
    periodStart: string; // ISO
    periodEndsAt: string; // ISO
    remainingTodayLovelace: string; // min(perDay - spent, balance - residue)
    availableNowLovelace: string; // the largest payment possible right now
    readAt: string;
  } | null; // null until the create is on chain
  float: { lovelace: string; low: boolean; readAt: string } | null;
  createTxHash: string | null;
  lastTxHash: string | null;
  inFlightRequestId: string | null;
  createdAt: string;
  updatedAt: string;
}

interface AllowanceReview {
  action: "create" | "top_up" | "revoke";
  allowanceId: string;
  unsignedTransaction: { encoding: "hex"; serialized: string };
  rawPayload: { kind: "cardano_tx_body_hash"; payload: string; signWith: string };
  estimatedFee: { lovelace: string };
  validUntil: string; // ISO; build again after this
  /** What the device must check before stamping (packages/shared/src/cardano-tx-check.ts). */
  expect:
    | {
        // create: checkCardanoAllowanceCreateTx(hex, {...expect, network, now})
        kind: "create";
        owner: string;
        ownerKeyHash: string;
        agentKeyHash: string;
        agentAddress: string;
        allowanceLovelace: string;
        floatLovelace: string;
        datum: AllowanceDatumView; // the device encodes it and compares byte for byte
        maxFeeLovelace: string;
      }
    | {
        kind: "top_up";
        owner: string;
        utxo: string;
        newLovelace: string;
        datum: AllowanceDatumView;
        maxFeeLovelace: string;
        validFrom: string;
        validUntil: string;
      }
    | {
        kind: "revoke";
        owner: string;
        utxo: string;
        maxFeeLovelace: string;
        validFrom: string;
        validUntil: string;
      };
}

interface AllowanceDatumView {
  agentKeyHash: string;
  perPaymentMax: string;
  periodMs: string;
  periodCap: string;
  periodStart: string; // POSIX ms
  spentInPeriod: string;
  allowedPayees: { kind: "key" | "script"; hash: string }[];
  expiresAt: string; // POSIX ms
}

interface AllowanceSpend {
  id: string;
  requestId: string;
  tool: "send" | "pay_x402";
  payee: string;
  lovelace: string;
  txHash: string;
  status: "signed" | "submitted" | "confirmed" | "failed";
  createdAt: string;
}
```

On-device checks (shared, used by the app before stamping):

- `checkCardanoAllowanceCreateTx(hex, e)`: plain body keys {0,1,2,3}, no witness; output 0 is a
  map output to `allowanceScriptAddress(network, ownerKeyHash)` (derived on the device from the
  compiled validator) with exactly `allowanceLovelace`, no tokens, and the inline datum equal byte
  for byte to `encodeAllowanceDatumHex(datum)`; output 1 is a plain output to the agent address
  (whose key hash is `datum.agentKeyHash`) with exactly `floatLovelace`; at most one more output,
  plain change to the owner; fee within `maxFeeLovelace`; TTL in the future.
- `checkCardanoAllowanceOwnerSpendTx(hex, e)` (top-up and revoke): body keys
  {0,1,2,3,8,11,13,14,16,17}, witness keys {5,7}; spends the shown allowance UTxO with one `Owner`
  redeemer (`d87a80`) and only the owner's allowance script; required signer = the owner; collateral
  back to the owner; top-up: output 0 back to the allowance with `newLovelace` and the shown datum;
  revoke: everything to the owner; validity window as shown; fee within the cap.

The app's approval screen should show: the budget, per payment and per day limits (fiat and ADA),
payees, expiry, the float, and that the agent can pay without asking within those limits.

## Agent-facing

`TransactionRequestResult.autoPay` (present when the request was auto-paid or is being):

```ts
autoPay?: {
  allowanceId: string;
  txHash: string | null;
  lovelace: string;
  remainingTodayLovelace: string | null;   // after this payment
  balanceLovelace: string | null;          // after this payment
  periodEndsAt: string | null;
  message?: string;                        // relay as is, see below
}
```

The request goes `APPROVED → SIGNING → BROADCAST → CONFIRMED` without an approval record;
`policy.decision` is `"allow"` with the reason `AUTO_PAY_ALLOWANCE`. For x402 the MCP worker's
`get_approval_status` (and `pay_x402`'s own follow-up) delivers the paid resource as usual. The MCP
tools tell the user `autoPay.message`, exactly: "Auto-paid 2 ADA from your on-chain allowance (no
tap needed); 3 ADA left today."

New policy reason codes:

| Code                         | Meaning                                                               |
| ---------------------------- | --------------------------------------------------------------------- |
| `AUTO_PAY_ALLOWANCE`         | Paid from the on-chain allowance (decision `allow`)                   |
| `ALLOWANCE_PAYEE_NOT_LISTED` | Fallback to passkey: the payee is not on the allowance's list         |
| `ALLOWANCE_LIMIT_EXCEEDED`   | Fallback: over the per-payment max or the period cap                  |
| `ALLOWANCE_INSUFFICIENT`     | Fallback: the allowance (or the float) holds too little               |
| `ALLOWANCE_EXPIRED`          | Fallback: the allowance has expired                                   |
| `ALLOWANCE_BUSY`             | Fallback: another payment from the allowance is still confirming      |
| `ALLOWANCE_UNAVAILABLE`      | Fallback: the chain could not be read, or the request is not eligible |

## Live demo (preprod)

1. In the app, open the agent, "Auto-pay on Cardano", set 10 EUR per payment, 20 EUR per day,
   budget 20 ADA, payee = the demo seller, 7 days. Approve the create with the passkey (one tap).
2. Wait for "Active" (about 20 s).
3. Ask ChatGPT/Claude to buy the address report: it pays without a tap and says so.
4. Revoke: one tap; the budget and the float come back to the wallet.
